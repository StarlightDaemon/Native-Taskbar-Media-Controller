### Category 6 — Configuration Risk

The project has no server-side configuration, no network-facing service, no CORS policy, no TLS configuration, and no database. Configuration is limited to the Windhawk mod settings block embedded in the `.wh.cpp` header.

The `Wh_Log()` calls present throughout the source are a Windhawk diagnostic API; they output to Windhawk's own log viewer, not to a public surface. This is standard practice for Windhawk mods and not a production debug flag concern.

**Finding OBS-2 (Info — no action required):** `LoadSettings()` clamps `offsetX` to 8 when negative (`if (g_Settings.offsetX < 0) g_Settings.offsetX = 8;`), but the clamped fallback of `8` is inconsistently different from the struct default of `200` and the documented default of `200`. This is a minor inconsistency: negative input is invalid, but the recovery value doesn't match the documented default. This is noted as an observation; it does not constitute a security or production risk.

### Category 8 — Open Observations (Speculative Pass)

**OBS-3 (Info — no action required):** The `forks/` directory (11 upstream source copies, ~30 MB total across all `.cpp` files) is tracked in git. This is intentional — the fork review process requires historical access — but it means every clone of this repository downloads all reference source files. For a public GitHub repository this is unusual. The operator may wish to consider converting `forks/` to a git submodule, a shallow archive, or a git-notes reference if clone size becomes a concern as the repository grows.

**OBS-4 (Info — no action required):** `OPEN_LOOPS.md` OL-2 references `fork-reports/synthesis-2026-05-19.md` for Phase 2 feature selection. That report exists and is complete. The open loop is valid but has been pending since 2026-05-19 (2 days at audit date). No urgency concern, but this is the only active gate blocking Phase 2 commencement.

**OBS-5 (Info — no action required):** The `GetFrameworkElementFromNative()` function at line 171 uses a hardcoded vtable offset of `+3` (24 bytes on x86-64) to locate the `IInspectable` shim inside a Windhawk `TaskListButton` implementation object. This is an ABI-level assumption that could break if Microsoft updates `Taskbar.View.dll` with a different vtable layout. This is an inherent architectural risk of XAML injection mods and is explicitly managed by Windhawk's hook mechanism. The `try/catch` wrapper provides a safe fallback. Noted for Phase 2 awareness; no immediate action needed unless breakage is observed.

**OBS-6 (Info — no action required, low-confidence):** `TriggerInitialScan()` launches a detached thread that calls `Sleep(200)` before posting `WM_SIZE` to `Shell_TrayWnd`. The 200ms fixed delay is a timing heuristic to allow Windhawk hook operations to settle before the scan fires. This is a common pattern in Windhawk mods and is low-risk, but it could fail on unusually slow systems. A future improvement could use an event signal from the hook rather than a fixed sleep.
